# 教程大纲（已审校）

本大纲经过知识拓扑审查，修正了原版的三处工程隐患：

1. **错误模型前置**：`std::expected<T,E>` 在 1.3 节引入，早于任何网络 API，避免第 2 部分出现未解释的关键类型。
2. **生命周期补全**：1.4 节专项讲解协程帧所有权与 fire-and-forget 的内存安全界限。
3. **buffer_ring 不割裂**：`receive_stream` 与 `buffer_ring` 基础在同一节（2.3）介绍，调优内容作为 Advanced 独立章节延后。

## 第 3 部分：系统韧性

> 前置：错误模型已在 1.3 节建立，此处直接进入复杂控制流管控。

| 章节 | 引入的核心概念 | 示例切入点 |
|------|--------------|-----------|
| 3.1 外部取消模型 | `stop_then`、协作式取消如何确保 I/O 资源确定性释放 | 给 sleep 加上可取消外壳，观察取消传播路径 |
| 3.2 局部时间约束 | `timeout` 两种实现机制：**link timer**（`IOSQE_IO_LINK` + `io_uring_prep_link_timeout`，零额外 syscall，约束 `single_shot_operation`）vs **独立 timer**（`when_any<Op, TimerAwaiter>` 竞速，支持任意 `cancelable_operation`，适用于 channel/stop_then 等非 io_uring 原语）；deadline 语义，两者错误码均为 `errc::timed_out` | 先用 link timer 给 `recv` 加超时；再对无法用 link timer 的 channel receive 用独立 timer，对比两段代码与错误处理的统一性 |
| 3.3 机制对比、错误分类与组合 | `timeout` vs `stop_then` 语义边界；错误分类矩阵（Error Taxonomy）：可恢复错误（如 `timed_out`）vs 必须收敛退出的错误（如 `operation_canceled`）；重试退避（retry policy） | 对照示例：同一场景分别用两种机制实现；用类型系统区分可重试与不可重试错误，驱动重试决策 |

## 第 4 部分：并发编排与资源收敛

| 章节 | 引入的核心概念 | 示例切入点 |
|------|--------------|-----------|
| 4.1 显式状态聚合 | `when_all`，返回 `tuple<expected...>` | 并发发两个请求，等双方完成后合并结果 |
| 4.2 竞速与抢占 | `when_any` 返回值规则：**同构**（所有操作 `resume_type` 相同）→ 直接返回 `expected<R>`；winner 失败也会立即返回并取消 losers；“异构 `variant` 路由”放到 4.4 Channel 章节再讲 | Hedged request（双副本竞速）+ SLA 抢占（主链路 vs deadline guard）+ 熔断打断长轮询（同构路径） |
| 4.3 任务树的协作取消 | `all`、`any` 组合器，子任务失败时如何通过信号链安全销毁同级协程帧；局部取消与全局事件循环状态的解耦（结构化并发的控制权收敛，避免悬挂任务泄漏） | 演示 `any` 的取消信号传播；对比 `when_any` 的底层语义差异；用 Mermaid 图展示取消信号如何在任务树中传播直至全部帧销毁 |

> **4.4 说明**：跨线程通信原语以 `ChannelPipe<T>` 为主；`Channel<T>` 用于单 IOContext 内任务协作。借此建立"每个 IOContext 拥有自己的线程；跨线程通过消息传递而非共享状态"的架构心智模型。`ThreadSafeChannel<T>` 当前为实验实现，不纳入对外教程主线。

## 写作指南
回归技术写作的第一性原理。一份优秀的工程化教程，其本质并不是一份“推销说明书”，而是一个**“心智模型构建器”（Mental Model Builder）**。特别是面对底层抽象或高性能系统架构时，教程的使命是建立读者对系统边界、资源流动和设计哲学的精确认知。

一个切实可行的“好教程”定义，可以拆解为以下6个核心维度：

### 1. 问题驱动，机制延后 (Problem-Driven Pragmatism)
优秀的教程永远从一个具体的、能够引起工程师共鸣的实际问题出发，然后再探讨解决该问题的机制为何如此设计。
* **切入点**：先描述一个现实场景（例如：“当网络线程和计算线程需要解耦时，共享状态加锁会导致不可接受的开销”），进而引出新的抽象机制（例如基于消息传递的 Channel）。
* **价值**：让读者在看到代码之前，先理解设计的初衷，明白该机制在架构拓扑中填补了什么空白。

### 2. 架构诚实与边界清晰 (Architectural Honesty)
技术文档必须直面复杂性，而不是用“黑盒”掩盖它。对于系统级开发，交代清楚底层物理事实是及格线。
* **资源管理与生命周期**：明确交代资源的分配与回收时机。每一个核心操作，都必须指明背后的内存模型、所有权转移路径以及资源的确定性释放（RAII）机制。
* **能力边界**：明确指出当前机制的适用场景与“反模式”。不隐瞒性能开销（例如：页面钉扎的代价），明确指出违反契约可能引发的后果。

### 3. 代码即契约 (Code as the Contract)
读者往往会将教程中的代码作为心智基础，甚至直接应用于工程中。因此，示例代码必须遵循最高标准的工程规范。
* **类型安全**：优先展示如何通过类型系统在编译期传递约束，而不是依赖口头警告。
* **零开销抽象**：代码示例应体现语言的核心优势，展示如何在不引入额外运行时负担的前提下进行抽象。
* **可推演性**：示例不应是零碎的片段。即使是简化的模型，其异常处理分支和状态转化也必须完整且经得起逻辑推敲。

### 4. 认知序列的线性递进 (Linear Cognitive Sequencing)
学习过程最忌讳“概念的突然跳跃”和“前置依赖缺失”。
* **单一变量原则**：每一个新的示例或章节，只引入一个全新的技术概念。
* **机制的闭环**：从底层的独立原语（如局部的等待组合）开始探讨，最终在宏观架构层面形成逻辑闭环（如整个事件循环的任务树收敛）。

### 5. 客观克制的行文风格 (Objective & Restrained Tone)
避免过度修饰、主观臆断和情绪化的表达（如“极其简单”、“框架神奇地处理了”）。
* **精确表达**：使用准确的工程术语陈述物理事实和约束条件。
* **事实说话**：让类型签名、状态机转移逻辑以及具体的操作机制来证明设计的优秀，摒弃多余的形容词。

### 6. 结构化视觉辅助 (Structured Visual Aids)
配图不能是随意的装饰，而必须是“文字无法表达的多维拓扑关系”的视觉降维。在高性能 C++ 框架文档中，图解应当承担起构建物理直觉的重任。
* **生命周期投影 (Lifecycle & Ownership)**：利用对象生命周期图或时序图，清晰标注资源（如 `io_uring` 的 Provided Buffers、协程帧、局部变量）在不同异步阶段的所有权交接边界。这是防御 Use-After-Free 心智盲区的最有效手段。
* **状态与拓扑 (State & Topology)**：用状态机图表达 `stop_then` 协作式取消的信号树状传播路径；用架构图界定同线程原语与跨线程原语（如 `ChannelPipe`）的系统隔离边界。
* **图解即代码 (Docs as Code)**：优先使用 Mermaid 或 PlantUML 等基于纯文本的绘图引擎。这不仅便于版本控制，更因为这类工具本身就带有严密的逻辑约束，能够防止画出“看似合理但在物理系统上无法实现”的架构图。

### 可行性自查清单（The Checklist）

为了让这个定义切实可行，当你写完一篇教程后，可以通过以下四个问题进行自查：

1.  读者看完这篇文档，能否准确推演出底层操作的内存流转或状态机转化？
2.  代码示例是否严格遵循了核心准则（如避免裸指针，使用视图类型传递契约）？
3.  文档是否解释了机制背后的“Why”（为何这样设计），而不仅仅是 API 的“How”？
4.  行文是否剔除了情绪化的冗余词汇，保持了冷静客观的技术推演？
