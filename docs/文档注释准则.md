# 文档注释准则（Doxygen）

目标：提高 API 的可用性与可维护性，而不是重复代码本身。

## 1. 写什么

1. 写 why，不写显而易见的 what。
2. 写行为契约：`@pre`、`@post`、错误语义、生命周期要求。
3. 写调用决策信息：何时用 A 接口，何时用 B 接口。
4. 写平台差异与编译条件（例如宏守卫导致的 API 可用性变化）。
5. 仅在必要时写最小示例，示例必须与仓库真实 API 一致。

## 2. 不写什么

1. 不给纯语法别名写“降噪式注释”（如“减少模板噪音”）。
2. 不复述函数名已经表达清楚的行为。
3. 不写与实现重复、无决策价值的句子。

## 3. 推荐结构

```cpp
/**
 * @brief <一句话描述设计动机>
 *
 * <2-4 行：说明为什么要提供这个接口，以及使用场景>
 *
 * @param ...
 * @return ...
 * @pre ...
 * @post ...
 * @throws ...
 */
```

说明：并非每个 tag 都必须出现，按接口复杂度选择。

## 4. 错误处理文档规则

1. `throw` 风格接口：明确 `@throws` 触发条件。
2. `std::expected` 风格接口：明确“不抛异常，错误通过 return value 表达”。
3. 析构函数：不传播异常时应明确说明策略。

## 5. 生命周期与并发规则

1. 参数需要跨 `co_await` 存活时，必须写出 lifetime 要求。
2. 输入输出缓冲（in/out）必须写清输入假设与输出结果。
3. 资源所有权转移（fd adopt、move）要写清 ownership 语义。

## 6. 示例规则

1. 示例优先最小可运行片段。
2. 类型名、namespace、返回类型必须与仓库现状一致。
3. 示例展示错误处理分支，不只展示 happy path。

## 7. 排版规则

1. 统一使用 Doxygen 块注释 `/** ... */`。
2. 注释星号列位对齐，避免混用不一致缩进。
3. 一段注释聚焦一个意图，避免长篇解释实现细节。

## 8. 评审清单（提交前）

1. 这段注释是否帮助调用者做决策？
2. 是否包含关键契约（pre/post/lifetime/error）？
3. 是否有低信息密度句子可以删除？
4. 示例是否与当前代码一致？
5. 排版是否一致且无漂移？
