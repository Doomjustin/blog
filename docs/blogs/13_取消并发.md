# 取消机制的演进：从手动拼装到隐式注入

这是在学习了capy的隐式注入玩法后的更新，解决了我原本混乱的思路，感觉眼神都清晰了不少。

---

## 旧版本的困局：`stop_then` 手动包装

旧版本就是让用户手工拼装，每个 awaitable 都得用 `stop_then` 包一下：

```cpp
co_await stop_then(some_io_operation(), stop_token);  // 得手动拼，十分繁琐
```

看起来没问题，但一旦涉及多线程，问题就来了。

### 坑一：跨线程 Data Race

问题的根源很简单：`stop_then` 一旦被触发（可能是后台定时器线程），就直接去调 `inner_operation.cancel()`。但同时，I/O 线程也在处理这个操作的完成事件。

```cpp
// 问题代码
stop_callback_.emplace(std::move(stop_token_), 
    [&]() {
        inner_operation.cancel();  // 两个线程同时修改，没有同步保护
    });
```

这就是经典的数据竞争：两个线程无序地读写同一块内存，导致随机段错误或诡异的逻辑错乱。

### 坑二：异步时差引发的 UAF（Use-After-Free）

为了解决 Data Race，可以用 `post` 把取消指令投递回 I/O 线程执行。但 `post` 是异步的，这又引入了新的问题。

看这段修补代码：

```cpp
stop_callback_.emplace(std::move(stop_token_), 
    [alive = alive_, &ctx = inner_.context(), target = &inner_]() mutable -> void {
        post(ctx, [alive = std::move(alive), &ctx, target] {
            target->cancel();  // target 可能已经被摧毁了！
        });
});
```

关键问题在于时序：取消任务排队等待执行，但底层 I/O 可能先完成——协程被唤醒，`stop_then` 这个局部对象随之析构——之后排队的取消任务才被取出执行——此时访问的 `target` 已经被释放了。

解决办法是在堆上引入一个 `std::shared_ptr<bool> alive` 作为生命周期守卫：

```cpp
std::shared_ptr<bool> alive_{ std::make_shared<bool>(true) };

~StopTokenWrapper() {
    *alive_ = false;  // 标记已销毁，通知滞后的 post 任务不要再访问
    stop_callback_.reset();
}
```

但这样每次取消都要额外分配一次 `shared_ptr`，成本也不低。

### 坑三：最关键的是用户的心智负担

真正的问题不是技术细节本身，而是**所有的复杂性都暴露给了业务代码**：

1. 编写 `co_await` 时需要考虑"这个操作是否需要取消？"
2. 如果需要，必须记得手动包裹 `stop_then`。
3. 遗漏任何一个，就会产生"无法取消的操作"，取消时挂起。

## 新版本的改进：隐式注入取消

### 设计动机：消除业务层污染

旧方案的致命缺陷不在技术复杂度，而在于**污染**。业务代码里到处是 `stop_then`，每个 I/O 函数签名都要添加 `std::stop_token` 参数，这直接增加了维护成本和开发者的认知负担。

```cpp
// ❌ 旧方案：取消把整个调用链都污染了
Task<> handle_client(IOContext& ctx, std::stop_token token) {
    auto res = co_await stop_then(async_read(fd, buffer), token);  // 得手动拼
    if (!res && res.error() == std::errc::operation_canceled) {
        // 处理被取消
    }
}
```

取消本来不应该是业务层的事。它应该像空气一样，无处不在但又看不见。

> **想法来源**：从 capy（C++ async runtime）的实现中得到启发，我发现可以用 C++20 的 `await_transform` 重新设计这一层。capy 为了通用性，通过 Env 注入 executor、allocator、stop_token 等参数；而我们的框架强绑定 io_uring，所以能更直接地在 promise 层注入 IOContext 和 stop_token，并统一依赖 ASYNC_CANCEL 语义。正因为这些都能确定下来，所以取消机制才能被完全自动化。

### 核心改进：三层隐式注入

**第一层：Promise 环境绑定**

每个 `Task` 的 promise 自动持有当前的 `IOContext` 和 `stop_token`，无需用户处理：

```cpp
struct StoppablePromise {
    IOContext& context_;
    std::stop_token stop_token_;
    // ...
};
```

**第二层：await_transform 统一拦截**

利用 C++20 的 `await_transform` 机制，框架可以在业务代码的每一个 `co_await IOAwaiter` 处进行拦截，自动将其升级为"取消感知"版本：

```cpp
// ✨ 新模型：零污染，框架自动处理
Task<> handle_client() {
    auto res = co_await async_read(fd, buffer);  // 框架自动注入取消机制
    if (!res && res.error() == std::errc::operation_canceled) {
        // 处理取消情况
    }
}
```

**第三层：统一落地语义**

`StopTokenWrapper` 在 awaiter 挂起期间隐式注册取消回调。被取消操作的最终结果由原操作的 completion 决定（cancel CQE 直接丢弃，不跟踪）：

```cpp
template<typename Promise>
auto await_suspend(std::coroutine_handle<Promise> handle) noexcept
    -> std::coroutine_handle<>
{
    auto inner_handle = inner_.await_suspend(handle, context());

    // 核心：在挂起期隐式注册取消回调
    if (promise_->stop_token.stop_possible())
        stop_callback_.emplace(promise_->stop_token, CancelFn{ this });

    return inner_handle;
}

// 取消触发时的统一路径
void CancelFn::operator()() noexcept {
    if constexpr (cancellable<Awaitable>)
        wrapper->inner_.cancel(wrapper->context());  // 若 Awaiter 实现 cancel，直接调用
    else
        wrapper->context().cancel(wrapper->inner_);   // 否则走 ASYNC_CANCEL
}
```

### 关键设计决策

1. **隐式注入**：用户编写普通的 `co_await`，框架在后台自动升级为"取消感知"版本。

2. **生命周期简化**：`stop_callback` 的生命周期严格绑定在 awaiter 挂起这段期间。不需要 `shared_ptr<bool>` 守卫了，cancel CQE 直接扔掉，不跟踪。

3. **awaiter 契约统一**：
   - 要是 awaiter 实现了 `cancel(io_context)` 方法，框架就调它。
   - 否则用默认的 `io_uring ASYNC_CANCEL` 方式。

### 核心代码对比

旧版本（用户手动拼）：

```cpp
auto task = [](std::stop_token token) -> async::Task<> {
    co_await stop_then(some_io(), token);  // ❌ 得手动传 token，手动调用 stop_then
};
co_await async::any(task(group.stop_token()), ...);
```

新版本（框架自动处理）：

```cpp
auto task = []() -> async::Task<> {
    co_await some_io();  // ✅ 啥都不用干，框架已经全搞定
};
// stop_token 框架内部在 Task::promise 里已经绑了，用户看不见
```

实现在 `src/async/stoppable_promise.h`：

```cpp
template<typename Awaitable>
auto await_transform(Awaitable&& awaitable) -> decltype(auto)
{
    using Tag = std::remove_cvref_t<Awaitable>;

    if constexpr (IOAwaitable<Awaitable>) {
        return StopTokenWrapper<Awaitable>{ std::forward<Awaitable>(awaitable), this };
    }
    else {
        return std::forward<Awaitable>(awaitable);
    }
}

// StopTokenWrapper 中的 await_suspend
template<typename Promise>
auto await_suspend(std::coroutine_handle<Promise> handle) noexcept
    -> std::coroutine_handle<>
{
    auto inner_handle = inner_.await_suspend(handle, context());

    if (promise_->stop_token.stop_possible())
        stop_callback_.emplace(promise_->stop_token, CancelFn{ this });

    return inner_handle;
}

// 取消触发时的路径
struct CancelFn {
    StopTokenWrapper<Awaitable>* wrapper;

    void operator()()
    {
        if constexpr (cancellable<Awaitable>)
            wrapper->inner_.cancel(wrapper->context());  // 若 awaiter 实现 cancel 方法，调用它
        else
            wrapper->context().cancel(wrapper->inner_);   // 否则使用默认的 ASYNC_CANCEL 方式
    }
};
```

关键改进：
- `await_transform` 在 promise 层拦截所有 IO awaitable，无需用户操心。
- `stop_callback` 不需要 `shared_ptr` 守卫了，生命周期由栈帧保护。
- cancel 工作的责任从用户转到框架，框架内部处理所有复杂性。

## 多线程下的行为对比

### 旧版本

```
主线程 (IOContext.run())
    ↓
    [处理 I/O 完成事件A]
    ↓
    task 协程被唤醒
    ↓
    stop_then 析构（alive_ = false）
    ↓

后台定时器线程
    ↓
    [发送 stop_token cancel]
    ↓
    post 任务进入队列
    ↓
    [IOContext 取出 post 任务，检查 alive_]
    ↓
    *alive_ == false，安全丢弃
```

陷阱：如果 post 任务执行前，协程没析构，就访问了已 free 的内存。

### 新版本

```
主线程 (IOContext.run())
    ↓
    task 协程开始 co_await some_io()
    ↓
    await_transform 自动把它包装成 StopTokenWrapper
    ↓
    stop_callback 被注册在 wrapper 的栈帧上
    ↓

后台定时器线程
    ↓
    [stop_token 被触发]
    ↓
    stop_callback 立刻在这个线程上执行（标准库保证线程安全）
    ↓
    调用 awaiter.cancel(context) 把 cancel 指令 post 回主线程
    ↓

主线程 (IOContext.run())
    ↓
    [从事件循环取出 cancel 指令]
    ↓
    发送 ASYNC_CANCEL SQE 给内核
    ↓
    原操作的 CQE 返回 -ECANCELED 或原结果
    ↓
    awaiter 恢复协程，返回错误给上层
```

新方案的好处：
- `stop_callback` 本身线程安全（标准库保证）。
- cancel 动作在 IOContext 里执行，安全、可控。
- 栈帧生命周期自动保护，不需要 `shared_ptr` 守卫。

---

## 总结：设计思路的转变

旧方案的问题很明确：所有的复杂性都暴露给用户。手动 `stop_then`、手动传 `token`、手动考虑哪些操作需要取消。

新方案的核心改变：**把复杂性从用户转移到框架**。框架在 `await_transform` 这个关键点进行统一拦截，所有的 IO awaiter 都被自动升级为"取消感知"版本。没有遗漏的可能，不依赖用户记忆。
